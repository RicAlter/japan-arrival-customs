# 运营Excel适配第一阶段（0.8.0-rc.3）

仅接KMT第3步业务确认表＋第4步申报准备表，按表头识别，附件名称不限。第3步应带箱重页。附件缺失、重复角色、编码＋箱号无法唯一配对、材质/品类/原产国冲突、无依据无码行或公式异常均返回 `needs_input` 并写入输入问题报告。不造编码，不把内部名转作申报名。第4步已填海关价格则作为成品拒绝，须另在历史对照角色提供。

运营说“处理已确认运营表”。WorkBuddy使用原有请求入口：

`python -B scripts/run.py --output <独立持久输出目录> workbuddy --request <本次请求文件>`

初次请求包含 `message=处理已确认运营表` 与 `files=[第3步路径,第4步路径]`，可选 `comparison_files=[第5步路径]`。程序返回 `needs_confirmation`、行数、`source_bundle_hash`、`special_conversion_hash` 和特殊数量换算清单。此时不生成工作簿。

业务明确确认本批业务计价单位、内部数量单位、申报单位及所展示的换算范围后，WorkBuddy构造 `units_confirmation`：`business_unit`、`internal_unit`、`declaration_unit`、`reference`、`confirm=true`，附第一次返回的两个哈希。本期支持件/个/盒/套/包/张/枚/支/只/本，业务和内部单位须一致。一次批次确认覆盖所列特殊换算；如果其中部分不成立，应先补充/更正原表再重新导入，第一阶段不提供逐行换算编辑UI。确认依据与身份分开记录，Excel或请求不能自证可信身份。

第三方调用也可使用 `python scripts/adapt_operations.py --output ... --request ...`，请求省略 `message`，其余相同。主Skill只使用一个业务入口。

成功目录包含 `standard/confirmed-arrival-v1.xlsx`、`evidence/provenance.json`、`batch.json`、`pair/`。原文件、配置版本与标准文件全部绑定SHA；每个使用字段保留原路径、表名、行列、原值、公式、缓存、复算依据，派生字段列出全部前置字段。数据文件放安装目录外，与附件目录隔离。相同来源和确认可重读核验，拒绝覆盖不完整运行现场。

第3步金额是唯一业务基准。历史338类金额差异存在来源清单中，`applied=false`。非精确海关单价由rc.2留空，内部金额继续保留。HS、日期、关务依据等正式缺项不会阻断具备必要数据的受控草稿。没有第6步税参数接入，第一阶段税金为空；正式输出始终关闭。

可追溯公式只支持映射配置列出的同一行二数相乘（第3步业务金额、箱组总重），缓存必须存在并与精确复算一致。已识别的尾部汇总单独排除并核对箱数/总重。未命名列重排无法确定时拒绝，不按相似数据猜列。无码但需跨表关联的行会明确报待补，不按出现顺序配对。

安装要求：支持文件型Skill的WorkBuddy；Python 3.11及以上；`openpyxl==3.1.5`；可执行本地脚本、读取持久附件、创建独立输出及显示/保存xlsx/json。无需Node、数据库、网站或飞书权限。开发端可移植CLI验证通过不等于WorkBuddy实机验收，原生触发、单位确认上下文、附件路径寿命及双表显示/保存仍须集中实测。
