处理日本到货时使用本主 Skill。Python 是确定性数据核心，WorkBuddy 负责接收附件、展示来源、收集业务确认和调用脚本。不要让 AI 自行宣布审核通过。

rc.6的“生成海关和内部到货表”使用已验收的历史第5步33列海关版式、第6步20列内部版式及8列箱重页。均为受控草稿，主表仍从第1行表头、第2行商品开始。未确认单价、申报数量、税金留空；缺值公式返回空白。旧12/21列技术草稿仅用于历史兼容，不作为最终业务模板。

业务需要看已上传回传候选时，在“生成海关和内部到货表”的统一请求中附当前`preview_id`。程序重新核验B2登记和归档，品名/材质只作候选展示；不会提交回传或创建D1决定。过期、未登记、跨批次预览拒绝。不要直接读取历史成品行号填数。

本轮只建设本地商品基础资料库及原表预填；不扩展D2/D3，不把资料库候选转成跨JAN自动归类规则。

先读 [0.7.0操作与技术边界](references/v070-operation.md)、[P2-B2实际回传](references/p2b2-return.md)及[P2-D1独立决策库](references/p2d1-library.md)。本版继承事件幂等、四层归档、有效检索和库外存储；D2生成候选与回放报告，D3须可信身份、D08和已批准质量策略。正式学习样本以D1实际统计为准，检索命中保持候选。

先读 [P2-B1精简业务审核](references/p2b1-compact.md)。[P2-A字段合同](references/p2a-intermediate.md)保留为底层与历史技术基线，业务不填写192列。既有审核见[P1-C流程](references/p1c-workflow.md)，来源合同见[P1-B流程](references/p1b-workflow.md)，调用见[审核协议](references/protocol.md)，字段语义见[数据合同](references/data-contract.md)。

1. 使用统一入口 `python scripts/run.py --output <独立目录> workbuddy --request <请求JSON>`。WorkBuddy负责从附件与明确业务表达形成请求，Python只路由到既有受控步骤。保留原件，输出目录、交付目录和SQLite资料库必须与原件及Skill安装目录分离。优先识别日方原始工作簿 `invoice (計算)` 第17行的已批准布局及同工作簿 `重さとサイズ` 页；结构无法唯一确定时提示缺失/冲突。文件名不作为判定依据。
2. 业务只提供原始日方工作簿即可说“处理这批日本到货”。程序读取明确表头布局中的商品编码、日文描述、产地、单价、Qty、Subtotal，生成未确认的第三份初步业务整理表和已登记的三页精简审核表。Subtotal合计只作为初步到货总价；Qty保留仓库点货的最大到货单位数量，单位须回查开定/商品资料，未知时不得解释为件或自动换算。此路径不会生成、签核或冒充第3步权威金额表。
3. 商品资料库由独立 `japan-arrival-product-library` Skill 初始化、导入和写入；本主Skill只读查询安装目录外的共享SQLite。处理原表时在请求中提供 `product_library`；合同绑定SQLite文件哈希，编码＋版本／日文名能够确定且无实质冲突时，程序直接复用历史中文名、品类、渠道、YD及版本。采购订单标题不是中文名，版本文字只是身份线索而非盒规；包装文字仍仅为候选，历史/官方材质仅作来源资料，BOX、全几种、订单数和历史盒装数不自动换算。只有无命中、版本不匹配、真实冲突和缺失项进入现有精简Excel异常。资料库不调用D1、不创建归类审批或自动规则。
4. 默认是**单人业务模式**：原始导入自动生成内部输入记录和版本，不要求业务填写合同JSON、签核令牌或审核角色。业务只在修改后的审核表预览差异后明确说“确认并保存这批审核”；系统保存一条不可覆盖的基础商品资料修订，并尽量记录宿主提供的操作者/会话上下文。宿主未提供可靠身份时，记录为未验证的本地业务确认，绝不冒充D08、独立关务批准或正式放行。兼容历史第3步文件的旧路径，但必须标识其来源，不能把程序初步整理冒充人工确认金额。
5. 导出 `review-package`，先补齐普通商品字段，呈现明确行范围和来源供业务批量确认。无前台/YD可按实际原因补录，不编造编码。商品/身份争议另列；价格、材质、盒规、税率争议保留在专业域。批量混入争议、未知行或旧确认时整次拒绝。
6. 业务确认一次只保存结构化的基础商品资料（中文名、申报品名、品类、渠道、YD及其说明）；正常项可批量处理，未匹配/冲突/单位不明项才要求补充。YD是内部参考，空缺不阻断该模式，也不虚构。材质、盒规、税率和归类仍属专业域，不能借单人商品确认批准；不产生D1学习事件。尾差算法未批准，不调整单价。原始Subtotal、初步整理金额、最终申报金额分层保存；整批合计正确不等于逐商品金额获批。
7. 使用 `status` 和 `professional-queue` 展示分域未决项。`render-drafts`只从同一状态生成海关和内部两份受控草稿并重读核验，未知盒规/税率不填计算值，海关隔离内部名称/YD/渠道。箱重核对放在两份草稿内，不生成第三份物流单。`formal-export`始终拒绝，没有自动外发功能。

本包包含 0.7.0 技术链路：`d2-report`与`d2-replay`只生成候选、支持统计、冲突和时间回放可用性；`rule-*`保存受控规则草稿及技术发布链，但未配置真实发布身份、质量门槛和显式生产开关时始终转人工。`source-status`仅报告本地Excel可用性及飞书/官网是否已实际配置，不能把模拟适配器说成已接通。B1仅导出接口继续保留；实际闭环用return-export/return-preview/return-commit，先展示差异再取得明确确认，不从空白或“采用候选”自行构造专业批准。最终选择与税号税率条件分层、分域保存，草稿不学习。前台状态非必填，无YD保留真实原因；不填写24栏申请人。可信管理员会话还须匹配D08，不能使用Excel自报身份。旧API不能绕过B2敏感字段版本化审核；F1/F2、正式输出关闭不变。原生触发、D1实机拒绝和实际显示/保存仍待完整Skill后集中验收；本地测试不冒充WorkBuddy证据。默认Python/openpyxl和标准库sqlite3，不依赖Node。

候选的 WorkBuddy 路由只接受以下固定意图，路由本身不执行审批：

- “处理这批日本到货” → 原始日方工作簿路径自动生成初步整理与已登记审核表；同源重复执行恢复同一批次。原始合同未签核时只能待审及草稿。旧版第3步输入路径继续兼容。
- “检查这批能否开始” → 一次列出依赖、原件、合同单位、D08身份、输出与D1库待办；不是批准。
- “确认并保存这批审核” → 对已展示的 `return-preview` 明确确认；默认单人模式仅保存本批基础商品资料修订，并生成可追溯的商品维护队列。由商品维护Skill写入共享资料库后，后续同条件才会复用。它不需要D08令牌，也不批准专业域、不会同步D1，更不会生成正式文件。
- “准备/填写/签核这批业务合同” → 仅保留给历史兼容/专业受控流程；签核必须明确确认哈希、依据与宿主可信contract角色，不能手改JSON补造批准。
- “预览/确认这批单位换算” → 原packaging审核域，先确认商品身份，展示各层单位、系数与来源，再由可信packaging角色明确提交；不改第3步金额。
- “生成这批到货的审核表” → 返回当前批次已登记审核表；材质历史可为空，推荐与官方材质仅在确有来源时传入。
- “这是我修改后的审核表，继续处理” → `return-preview`；必须展示差异与确认哈希。日常基础商品资料可由单人明确确认保存；含材质、归类、税率、盒规或未解析文字的回传保持待专业受控处理。
- “查看这批还有哪些问题” → `batch-brief` 和既有 `status`/`professional-queue`；不以摘要代替逐项门禁。
- “生成海关和内部到货表” → `render-drafts`；仅受控草稿，正式输出仍由 `formal-export` 门禁拒绝。

`workbuddy-route`按受控模板结构识别原始发票、历史加工表、箱重页及三页审核回传表；文件名不会参与识别。多个同类结构、未知结构或原始发票与历史第3步同时出现时停止并提示澄清。审核提交后的 `return-commit --library <安装目录外D1库>` 会在成功保存B2决定后尝试同步D1；同步失败仅给出可重试状态，绝不回滚已保存审核决定。`historical-references`只显示D1正式且当前有效的案例候选；候选绝不自动采用。正式学习样本为0时如实显示0。
